# Runbook：数据泄露

适用于：数据库或对象存储被未授权访问、私有内容可被公开读取、密钥泄露后发现被利用、日志中出现不该有的个人数据等。

## 1. 遏制（第一个小时）

- 打开 kill switch：视情况关闭 `uploads`、`publish`、`signups`，必要时 `read_only`。
- 轮换相关密钥（见[密钥轮换](rotate-secrets.md)）：数据库口令、R2 凭证、`BETTER_AUTH_SECRET`（会让所有人重新登录）。
- 如果是私有对象被公开：确认 public 桶里只有 public Release 引用的对象；把误放的对象删除并清除 CDN 缓存。
- 保留现场：导出相关时间窗口的 Railway 日志、Cloudflare 日志、审计日志（`verifyAuditChain` 确认审计链未被篡改）。

## 2. 评估影响

- 哪些数据：账号邮箱、OAuth 身份、私有 Creation / Release、上传原件、法律请求中的申请人信息（这部分是加密字段，确认密钥是否也泄露）。
- 影响多少用户、哪些地区（美国 / 欧盟）。
- 时间窗口：从什么时候开始、什么时候被遏制。

## 3. 通知

- **GDPR**：涉及欧盟用户个人数据、且可能对其权利造成风险时，在知悉后 **72 小时**内通知主管监管机构；高风险时同时通知受影响用户。运营主体和主管机构确定前，由 owner 决定并咨询法律顾问。
- **美国各州**：按各州数据泄露通知法评估（涉及邮箱 + 口令等组合时通常需要通知；char.pub 不存储口令）。
- 在站内发布说明：发生了什么、影响范围、用户需要做什么。

## 4. 修复与复盘

- 修复根因，补充回归测试（尤其是授权矩阵测试中的遗漏）。
- 写复盘文档：时间线、根因、影响、改进项。
- 在 DECISIONS 中记录由此产生的设计变更。
