# LOOP（执行契约）

## How to launch

先读 `docs/goals/v0/LOOP.md` 和同目录下的 PROGRESS.md，确认它们描述的目标与当前请求一致。然后以 VISION.md 为意图、DOD.md 为验收标准，继续做已获授权的工作。如果执行被中断，要为下一个会话留下足够的状态。

权威顺序：用户最新的指令 > `DECISIONS.md` > `spec/` > `docs/design/` > 本目录下的文件。发现冲突时，先对齐文档再动代码。

## Preserve the goal

- 这个包由用户的意图和授权支配。VISION、DOD 和 DECISIONS 要与用户当前的指令保持一致。
- 实现违背约定的成果时，修改实现；有用户指令或已核实的事实作为依据时，修正过时的文档。修改用户拥有的范围、成果或验收标准之前，必须先得到用户的决定。每次修改都要记下理由，让下一个 agent 能分辨这是纠错还是新需求。
- **规范优先**：canonical-model 和 context-ir 是规范。实现时发现规范有歧义，按“最小改动 + 追加 DECISIONS 条目 + 同步更新一致性用例”的方式处理，并告知用户，不要在代码里悄悄做出选择。
- **本项目的固定约束**（来自用户）：
  - 仓库 public，密钥不进 git。
  - 优先采用成熟方案，不重复造轮子。
  - 本地开发统一使用 pnpm（安装、脚本、workspace），不生成 `package-lock.json`（D-125）。
  - 代码注释和 llmdoc 要自包含：直接写清规则和原因，不堆砌“§x.y”“D-xxx”这类章节或决策编号（过程文档如 PROGRESS / DECISIONS / commit 不受限）。
  - 单次写入的代码不超过 2000 行，大文件分多次追加。
  - 开始工作前先 `pwd`，文件工具只使用真实的绝对路径。
  - 做大范围探索、规划或文档工作之前，先加载 `llmdoc` skill。
  - 非平凡的计划或编辑要先与用户对齐。

## Choose useful work

- 依据真实的依赖、风险和反馈选择下一步工作。里程碑用来组织目标，但不禁止推进其他独立的工作。建议的依赖顺序：M0 → M1 → M2 → M3（M3 可以与 M4 并行）→ M4 → M5 → M6 / M7 → M8 → M9 → M10。
- 风险高的工作先做：canonical 与 digest（M1-3）、Resolver 的字节级确定性（M2-1、M2-5）、授权（M4-3）、OIDC（M7-2）、tombstone 级联（M5-5）。
- 只使用宿主支持并已为本任务授权的工具、委托方式和提交方式。本文件不授予任何额外权限。以下操作**每次都要单独征得用户同意**：
  - force push 到 `char-pub/char`（覆盖旧仓库）；
  - 修改 GitHub 组织设置；
  - 创建或修改 Railway、Cloudflare 上会产生费用或对外可见的资源；
  - 部署 production；
  - 发布 npm 包；
  - 创建 GitHub App 或 OAuth App；
  - 以任何形式对外发布内容。
- 失败的尝试如果提供了新证据，就是有用的。只要有可行的路径，就重试或换一种方法；当尝试不再带来新信息时，找出缺少的决策、资源或能力，转去做其他独立的工作。把解锁条件记进 PROGRESS，避免恢复后的会话重复走进同一条死路。输入发生变化时，重新检查阻塞项。

## Make acceptance mean something

- 只有在 DOD 条目的预期结果被证明之后才能打勾。记录命令和结果、可重复的流程和观察结果，或者写明审阅人和结论的人工验收。大段日志放在 `docs/goals/v0/evidence/` 或 CI 链接中，PROGRESS 里只放引用。文件存在或尚未执行的检查都不能证明行为。
- 一致性测试集的预期输出必须经过人工审阅后才能提交，不允许把当前输出直接写成预期结果。
- 验证力度要与改动的影响和约定的验收标准相匹配。工作过程中运行相关检查；里程碑验收和最终完成前运行完整回归（`pnpm ci:all`）。后续改动如果使先前的证据失效，重新打开受影响的条目并取得新证据。要求的检查失败、被跳过或无法执行时，验收保持待定，记下原因和受影响的工作。

## Preserve enough state to resume

维护 PROGRESS.md：当前目标、包路径、正在进行的工作、证据和阻塞项。它的摘要要与 DOD 的勾选状态一致。有意义的决策和结果要在出现时就记下来。交接时，PROGRESS 要能说明现在什么是真的、接下来能做什么，不需要回放整段对话。重要的决策同时写入 `DECISIONS.md`（从 D-110 起按顺序编号）。

## Completion and blocked handoff

- 只有同时满足以下条件，才能宣布 **ALL DONE**：DOD 的每个条目和每条全局验收都在最终状态下满足；VISION 的每条成功标准和每个用户案例都被覆盖；完整回归通过；用户的人工验收（G-5）已记录；最终证据的引用已写入 PROGRESS。
- 如果剩下的有用工作全部被未解决的外部前置条件或用户决策阻塞，报告 **BLOCKED**，并列出受影响的条目和确切需要的输入或动作。暂停、验证失败或阻塞交接都不算完成。如果宿主提前结束会话，要记录实际状态和下一步工作，不要声称已满足任何一种结束条件。
