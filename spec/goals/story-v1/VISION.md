# Story v1 改造目标

## 目标与授权

2026-09-30 用户要求按 `spec/story-v1.md` 及本轮评审开始执行；当前无用户，允许破坏性重构。主规范见 [story-v1](../../story-v1.md)，决策见 [DECISIONS](../../../DECISIONS.md)。执行包路径为 `spec/goals/story-v1/`。

目标是让创作者组合人物、场次、资料与 Prompt，发布完整的静态作品，供独立 Runtime 消费。范围包含本仓库的 Core、Assembler、SDK/CLI/Action、Registry 和 Web 创作工作流；不在此仓库托管真实游玩；用户追加授权建立独立 harness monorepo，为 Runtime 准备，并直接考虑 Jev/Laya 决策提供方。候选起点为 deepseek-ai/deepseek-harness，先核实代码、许可与边界。

无需保留旧格式、旧摘要或旧 messages 的逐字节兼容，不维护两套组装器。仍保留来源、许可、身份完整性、权限、确定性和纯计算边界。允许迁移仓库内示例与 fixture；规范 expected 的人工接受仍为独立步骤。未授权生产数据清理、部署、云资源创建、公开发布或远端强制推送。

## 成功标准

- S1：作品能表达参与者实例、场次、作者行动建议、Beat/Ending、事件/时间线、条件/效果及知情；简单作品无需高级配置。
- S2：玩家带人进入/离开场次、选择未预设行动时，Runtime 的实际局面能通过消费契约准确反映，静态定义不被改写。
- S3：资料有稳定身份和渐进目录；按视角保护正文、目录与 Selector 输入；确定的输入可重放组装。
- S4：Style/Preset/Module 有明确范围、装配、预算、来源和可用能力。
- S5：发布、草稿构建、授权消费、投稿/Remix/协作、Web 编辑预览使用同一契约，出错可定位和恢复。
- S6：示例、文档、schema、工具和验收一致；工程门禁及本地端到端验证通过。

## 代表案例

- U1：选 Alice/Bob，写一场戏，预览并发布；不写变量或条件也成立（S1/S5）。
- U2：玩家把 Bob 带入作者默认只安排 Alice 的后门场次；实际在场名单生效（S2/S3）。
- U3：同一 Character 作为两个保安使用，独立修改、知情、口吻与来源（S1/S3）。
- U4：作者列出交信/烧信/留信，玩家自行抄信后交出；建议不自动执行效果（S1/S2）。
- U5：Bob 不知道秘密，Selector 和生成上下文均看不到秘密状态；已授权直接关联的资料节在 skip 下仍按预算可用（S3）。
- U6：重复确认 Beat 不重复加信任；未知 judge 的否定不能触发拒绝结局；stop 后无法继续推进（S1）。
- U7：三层资料分组可达，同模块多位置装配可重放，过期 Plan 被拒绝（S3/S4）。
- U8：作者构建草稿交授权 Runtime；协作者可改草稿不可发布；投稿按对象合并并校验；有损导出明确说明（S5/S6）。
