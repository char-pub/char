# 作者工作流 v1：创作、试玩、分享与参与

> **Superseded（2026-09-30）**：本文是讨论过程记录，现行规则以 [Char Story v1-draft](../../story-v1.md) 与 [DECISIONS](../../../DECISIONS.md) D-162 至 D-174 为准。文中“已确认”的取舍已按统一规范修订，二者冲突时以统一规范为准。

日期：2026-09-26。状态：**讨论稿 / Proposed**，不修改现有 Web 实现。

本文是总稿第 15 节“阶段 5：设计作者工作流”的产出。它把前几轮定下的结构（[剧情结构 v1](story-structure-v1.md)、[资料与 Prompt 组织 v1](content-and-prompt-v1.md)、[消费契约 v1](consumption-contract-v1.md)）串成作者和玩家实际走的路径，并对照现有 Web 实现，指出哪些可以沿用、哪些需要新增。

完成标准来自总稿第 15 节：**普通作者能先写内容，高级配置按需出现。** 本文还按总稿第 16 节检查“易于创作、分享、使用、参与”四个目标。

## 1. 现状

以下是 `apps/web` 目前的作者流程，作为设计起点：

| 环节 | 现有实现 | 本文的处理 |
|---|---|---|
| 新建 | 先选九种类型之一，再填名字和地址；没有模板 | 改为从“想做什么”出发（第 2 节） |
| 导入 | Character Card V2/V3 导入向导，确认评级、权利和许可 | 沿用 |
| 编辑器 | 整页表单：基础信息 → 按类型的配置 → “More options”（段落、依赖、评级、语言）；右栏发布前检查；自动保存 | 保留整体结构，Scenario 新增“剧情”工作区（第 3 节） |
| 预览 | 手动构建草稿预览，可设 persona、历史、manual 开关、locale；显示 Trace 与 token | 扩展为视角与剧情状态预览（第 4 节） |
| 作者测试 | Scenario 与 Preset 的确定性 fixture | 扩展 fixture 输入，沿用断言方式 |
| 投稿 | 在最新 Release 上改、增、删文本段落和部分元数据；作者审核后进入草稿 | 扩展为剧情对象投稿（第 6 节） |
| Remix | Web 端没有入口 | 新增（第 6 节） |
| 发布 | 选版本号与可见性，异步检查依赖与许可 | 沿用，增加能力声明与差异提示 |
| AI 辅助 | 没有写作辅助；只有 agent 标记与 Agent Token | 新增起草类辅助（第 7 节） |
| 试玩 | 没有；预览只看组装结果 | 接入官方 runtime（第 5 节） |

GitHub 绑定的 `char.yaml` 发布通道保持不变，是进阶作者的另一条路径。

## 2. 从“想做什么”开始

新建页不再让作者先理解九种类型，而是先问想做什么，再映射到类型与起始层级：

| 作者选择 | 创建的作品 | 起始层级 | 编辑器首先展示 |
|---|---|---|---|
| 一个角色 | Character | L0 | 名字、介绍、开场白、头像 |
| 一个故事或情境 | Scenario | L1 | 选角色 → 第一个场次卡片 |
| 一个世界或设定集 | World 或 Lorebook | L2 | 世界介绍 → 条目列表与分组 |
| 一种文风 | Style | L0 | 风格说明与示例 |
| 玩家身份 | Persona | L0 | 名字与介绍 |
| 高级：Preset / Prompt Module / Relationship | 对应类型 | — | 现有编辑器 |

“一个故事或情境”是本轮的主要新增路径：

1. **选角色**：从自己的作品、收藏或搜索结果中选一个或多个 Character，也可以当场新建一个只有名字和介绍的角色。选中的角色成为依赖，版本自动锁定。
2. **写第一个场次**：一张卡片，包含时间地点、开场局面、在场人物，以及每个人在这场的身份（`part`）和目的（`goal`）（F-27）。
3. **可以直接试玩**（第 5 节）。

到这一步作品已经是完整的 L1 作品，可以发布；没有要求写 Beat、结局或条件。

**模板**：新建页可以提供少量官方示例作为起点（例如“两人对峙的一场戏”“多角色开放情境”），内容就是可以 Remix 的普通作品，不是特殊机制。

## 3. Scenario 编辑器的“剧情”工作区

现有编辑器对 Scenario 显示 Cast、bindings、推荐 Preset 与 assembly。本文新增一个“剧情”工作区，其余部分移到“设置”中。

### 3.1 布局

```text
┌ 剧情 ───────────────────────────────────────────────┐
│ 视图：[场次] [剧情线] [时间线]           + 场次  + 结局 │
│                                                      │
│ ┌ 停电后的大厅 ─────────┐  ┌ 后门与河边小路 ────────┐ │
│ │ 深夜 · 旅馆大厅       │  │ 进入条件：怀疑 Alice…  │ │
│ │ Alice 旅馆老板 · 保护…│  │ Alice · 住客           │ │
│ │ Bob 调查员 · 查清去向 │  │ 可能的变化：坦白       │ │
│ │ 可能的变化：怀疑、信任│  └────────────────────────┘ │
│ └───────────────────────┘                              │
│                                                      │
│ 结局：一起离开 · 真相公开 · 雪停之后                   │
└──────────────────────────────────────────────────────┘
右栏：人物 · 资料 · 物品 · 变量 · 知情（按层级逐步出现）
```

- **场次视图**：场次卡片按作者排列，卡片内直接编辑 `part`、`goal`、`scene.goals`（数据分两处存，界面合在一起，F-27）。
- **剧情线视图**：每条剧情线一行，引用的场次和 Beat 以卡片显示；拖动只改变引用，不复制内容。
- **时间线视图**：事件卡片与场次卡片按 Timeline 的相对顺序排列，并列的放在同一列；可以切换多条时间线（剧情结构 v1 第 6.7 节）。v1 不做精确日期与时长。

### 3.2 层级如何出现

| 层级 | 触发方式 | 新出现的入口 |
|---|---|---|
| L1 | 新建故事 | 场次卡片、人物的身份与目的 |
| L2 | 点“+ 可能的变化”“+ 结局”“+ 剧情线”“+ 事件”，或给场次关联资料 | Beat、结局、剧情线、事件与时间线、场次资料、进度展示 |
| L3 | 在任意条件处点“用规则表达”，或点右栏“变量 / 知情 / 物品” | 条件构建器、变量、效果、知情声明、Item、参与者级改编 |

一旦作品用到某一层，相应入口就保持显示；没用到时不显示空面板。L3 的条件入口默认是“用一句话描述”（生成 `judge`），旁边提供“用规则表达”（F-28）。

### 3.3 条件构建器

- 三类可选条件：进度（场次、Beat、结局）、知情（谁知道什么）、变量；只列出存在的对象和类型匹配的变量。
- 组合用“全部满足 / 任一满足 / 不满足”三种分组，对应 `all` / `any` / `not`。
- 超过 8 层或 64 个节点时显示警告和拆分建议（第一轮取舍 6）。
- 已有的一句话条件可以一键改写为规则；可以让 agent 起草规则版本，作者确认（第 7 节）。

### 3.4 知情

知情编辑有两个入口，写入同一份 `story.knowing`：

- 在条目卡片上点“谁知道这件事”，为每个参与者选“知道 / 不知道 / 未声明”；
- 在场次卡片上点“进入时谁已经知道”，只能增加（第一轮取舍 2）。

作品启用 per-agent 时，编辑器额外提示三类情况（消费契约 v1 的 P-1、P-2、P-3）：

- 哪些资料对角色不可见，提供一键标为 shared；
- 哪些人物没有 `outward` 片段，其他角色看不到他们的任何描述，建议把外貌等拆出来；
- 目的只给本人，需要别人知道时建议写成条目。

### 3.5 其他作品类型

- **Character**：基础信息之外，片段卡片增加“别人看得到”（`outward`）开关和 description 字段；只有一段介绍的 L0 角色不显示这些。
- **World / Lorebook**：左侧分组树（最多 3 层），右侧条目卡片；条目上有视角（设定 / 传闻 / 某人的说法）、`about` 与出处。上传文件即创建参考资料，可以按标题生成分节，作者确认后保存。
- **Style**：核心说明与示例分开，示例可以标为“按需”并写 description。
- **Preset / Prompt Module**：保留现有 policy 编辑器，块改为 `default_at`，新增 `placements` 列表，可以把同一块放到第二个位置（资料与 Prompt v1 第 7 节）。

## 4. 预览

现有草稿预览可以设置 persona、历史、manual 开关和 locale，显示 Trace 与 token。v1 在此基础上增加两类输入，都只用作者自己构造的合成数据，不调用模型（D-160）：

| 输入 | 作用 |
|---|---|
| 视角 | 旁白 / 某个参与者；切换后显示该视角的 Catalog 与最终消息 |
| 剧情状态 | 当前场次、开局、已达成的 Beat、变量值、知情状态；缺省为所选开局的初始状态 |

预览面板分三栏：

1. **Catalog**：`required`、`direct`、`candidates` 三组，以及 `withheld` 数量；作者预览中可以展开 `withheld` 看具体是哪些内容被过滤、为什么（消费契约 v1 第 6 节）。
2. **选择**：使用 `fixed` Selector，作者勾选候选内容模拟判定结果。
3. **组装结果**：最终消息与 Trace。

**条件检查**：预览面板额外列出当前状态下每个场次、Beat、结局的条件是否满足；`judge` 命题由作者手动设为真或假。这一项不需要 runtime，是条件语言 v1 的参考求值，只用于预览。

注意：总稿确认“char.pub 不提供运行求值器”，指的是不承担游玩中的求值。编辑器预览中的条件检查是作者工具，与一致性 fixture 使用同一份参考实现；它的结果不写入任何会话。

**保存为作者测试**：任意一次预览的输入（视角、剧情状态、选择）都可以一键保存为 assembly fixture，沿用现有断言方式（messages_digest、trace 断言或错误码）。fixture 的输入结构扩展为 TurnView 与 SelectionPlan。

## 5. 试玩

试玩在官方 runtime 中进行，与预览分开：预览看组装结果、可复现；试玩看实际体验、使用真实模型。

| | 预览 | 试玩 |
|---|---|---|
| 运行位置 | 编辑器（浏览器） | 官方 runtime |
| 是否调用模型 | 否 | 是 |
| 数据归属 | 作者的合成输入，可以保存为公开 fixture | runtime 中的私有会话 |
| 用途 | 检查内容是否正确进入上下文 | 检查作品玩起来如何 |

流程：

1. 编辑器顶栏“试玩”按钮先把当前草稿发布为一个 **private Release**，再在官方 runtime 中打开它。runtime 只读取 Release，不读取草稿（用户选择）。
   - 为避免版本列表被试玩版本淹没，试玩发布使用自动版本号（例如 `1.2.0-play.3`），在版本页默认折叠，可以批量清理；它们仍是普通的 private Release，照常经过发布检查。
   - 发布检查失败（例如悬空引用）时不能试玩，编辑器显示和正式发布相同的错误。
2. 作者可以选择开局、视角，也可以在 runtime 中跳到某个场次或设置变量（开发者模式），方便测试后面的场次。
3. 试玩中 runtime 显示当前场次、已达成的 Beat、变量变化；作者回到编辑器修改后再次点“试玩”，会产生新的试玩版本，runtime 提示“有新的试玩版本，是否重新开始”。
4. 试玩中发现问题时，作者可以把当前状态“保存为预览输入”，回到编辑器用预览复现。导出的是剧情状态和最近几条消息的摘要，不是完整聊天记录；最近消息作为合成历史保存前需要作者确认。

试玩会话属于 runtime，char.pub 不保存；聊天流量不经过 char.pub（D-055）。

## 6. 分享与参与

### 6.1 发布

沿用现有发布流程（版本号、可见性、异步检查），在发布面板增加：

- **能力声明**：自动计算的所需能力列表（剧情结构 v1 第 7 节），以及“官方 runtime：完整支持”的提示；
- **差异提示**：与上一版本比较时，按“正文 / description / 结构”分类（F-24），并列出删除或改名的对象被哪些依赖作品引用（仅作者可见的统计）。

### 6.2 作品页与分享

- 作品页显示“开始游玩”，打开官方 runtime；有多个开局时先选开局（总稿 16.3）。
- 作品页显示所需能力，以及许可、分级和是否允许改编。
- 分享卡片（链接预览）显示标题、简介、头像和“开始游玩”。

### 6.3 投稿

现有投稿表单只能改文本段落和部分元数据。v1 扩展为按对象投稿：

| 投稿类型 | 界面 | 对应变更 |
|---|---|---|
| 修改设定条目 | 现有段落编辑 | `fragment` |
| 新增或修改场次、Beat、结局、剧情线、开局、物品 | 与编辑器相同的卡片，只读原作，编辑自己的部分 | `story` |
| 修改知情声明 | 知情编辑器 | `story`（kind `knowing`） |
| 修改参与者的身份与目的 | 参与者卡片 | `cast` |
| 修改分组 | 分组树 | `group` |

投稿表单直接嵌入剧情工作区的只读视图：投稿者看到完整作品结构，在上面新增或修改对象，提交前可以预览。合并后重新校验引用，悬空引用视为冲突（剧情结构 v1 第 8 节）。

作者审阅时按对象显示差异；新结局、新 Beat 等以卡片形式显示，可以直接在预览中试一下。

### 6.4 Remix 与续作

新增两个入口，都在作品页上：

- **Remix**：复制作品的完整定义到自己的 namespace，记录 `derived_from`（relation `remix`）。复制后所有依赖仍然锁定原版本。许可不允许改编时不显示入口，只显示“投稿给作者”。
- **写续作**：新建 Scenario，把原作品作为依赖，自动带入 cast 与资料引用；新建一个开局，作者选择“从原作哪个结局之后开始”，编辑器按该结局的 `effects` 预填 `starts.set`，作者可以修改（剧情结构 v1 第 6.6 节）。

### 6.5 共同创作

现有权限以 namespace 为单位：个人 namespace 只有 owner，system namespace 有 maintainer。v1 采用**作品级协作者**（用户选择）：作者给单部作品添加协作者，协作者可以直接编辑草稿，不需要投稿。组织 namespace 不在 v1 范围。

- **权限**：协作者可以编辑草稿、试玩（发布试玩用的 private Release）、审阅投稿；正式发布、改可见性、改许可与分级、管理协作者只属于 owner。
- **并发编辑**：沿用现有的草稿版本冲突检查（If-Match / 409）。v1 不做实时协同；两人同时改草稿时，后保存的一方看到冲突提示，可以按对象查看差异后重新应用自己的修改。
- **署名**：协作者的修改记入 Revision，在 Release 的 contributors 中署名，与原作者 authors 分开。
- **许可**：协作者加入时确认贡献按作品许可授权，与投稿的规则一致（D-064）。

### 6.6 游玩沉淀为创作

在官方 runtime 中，玩家可以在任意时刻选择“保存为创作”：

1. 选择去向：**给原作者投稿**（新结局、新 Beat 或新场次）或**写成自己的续作 / Remix**（许可允许时）。
2. runtime 在本地整理草稿：用 agent 把最近的剧情概括成对象（场次卡片、Beat 或结局的 description），以当前场次、变量和知情状态作为 `starts`。聊天记录本身不上传。
3. 草稿在编辑器中打开，标注“由 agent 根据游玩整理”；玩家修改后提交。模型生成的文字需要玩家确认贡献权利（D-064），Contribution 标记 `agent: true`（D-065）。
4. 分级与内容提示从原作继承，发布时照常检查。

## 7. Agent 辅助

v1 的 agent 辅助只做起草，所有结果经作者确认才写入草稿：

| 场景 | 起草内容 |
|---|---|
| 缺少必填 description | Beat、结局、变量、分组、参考资料的 description |
| 长资料上传 | 按标题生成分节与分节 description |
| 一句话条件 | 对应的规则版本 |
| per-agent 提示 | 把人物介绍拆成外在描述与内心设定 |
| 游玩沉淀 | 场次、Beat、结局的草稿（第 6.6 节） |

规则：

- agent 起草的内容在草稿中标注来源，直到作者编辑或确认；
- agent 通过作者的会话调用，不能直接发布；
- 模型调用发生在官方 runtime 或作者选择的服务中，不经过 char.pub 后端，char.pub 不保存模型凭据（D-160）。

## 8. 按四个目标检查

| 目标 | 本文的对应 | 仍有缺口 |
|---|---|---|
| 易于创作 | 从“想做什么”开始；L1 一张场次卡片即可发布；层级按需出现；条件默认一句话；agent 起草 description；事件与时间线视图 | 时间线只有相对顺序，没有日期计算 |
| 易于分享 | 作品页“开始游玩”；分享卡片；能力声明；许可与改编提示 | 单独分享一个场次仍需 Remix |
| 易于使用 | 玩家从开局直接开始，不需要理解 Preset；进度展示由作者决定 | 第三方 runtime 的降级体验由各 runtime 自行实现 |
| 易于参与 | 按对象投稿；Remix 与写续作入口；作品级协作者；游玩沉淀为创作 | 组织 namespace 不在 v1；没有实时协同 |

## 9. 本轮取舍（已确认，2026-09-27）

1. **新建页从“想做什么”出发**，九种类型收到“高级”里。
2. **Scenario 编辑器以“剧情”工作区为主**，现有 Cast、推荐 Preset、assembly 移到“设置”。
3. **v1 提供 Event 与相对顺序的 Timeline**（用户选择，替代“v1 不做”的建议），见剧情结构 v1 第 6.7 节。
4. **编辑器预览提供条件检查**（参考求值，只用于预览和 fixture），不改变“游玩中的求值归 runtime”。
5. **试玩只能使用 private Release**（用户选择，替代“runtime 读取草稿”的建议）；试玩版本自动编号、默认折叠。
6. **共同创作采用作品级协作者**，组织 namespace 不在 v1 范围。
7. **游玩沉淀为创作由 runtime 在本地整理**，只上传整理后的定义。
8. **agent 辅助只起草**，所有内容由作者确认，agent 不能发布。
