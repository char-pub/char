## 1. 设计出发点

char.pub 帮助作者组织、组合并发布创作内容。角色、场景、剧情线和时间线沿用创作者能理解的概念；独立 Runtime 在这些定义上开展实际游玩。作者可以为自己喜欢的具体角色写专属剧情，也可以选择制作可替换人物的模板。

建议采用“明确的对象与关联，加上可以自由书写的正文”。结构化首先解决身份、引用、参与关系、适用范围和组织方式；人物性格、矛盾、动机等保留自然语言。不要把创作变成必须填完的大型属性表，也不要因为模型最终需要文本，就在作品定义中丢掉这些关联。

本轮讨论内容语义。context compile、检索、rerank、token 预算和消息位置消费这些语义；本轮不设计模型调用或运行状态推进算法。

后续用户进一步明确：内容定义从第一版就应考虑 description 优先的渐进暴露，并为独立 Context Engine 组织 Preset、Style 与 Prompt Module 提供契约。对应的当前实现核对与候选设计见 [渐进式内容暴露与 Context Engine 契约](context-engine-content-contract.md)。这会补充对象的可发现入口和使用声明，不改变本文以创作语义组织人物、场次与资料的出发点。

## 3. 先约定概念层级

| 概念 | 建议含义 | 首轮发布粒度建议 |
|---|---|---|
| Character | 一个可被引用的人物定义 | 可独立发布 |
| Scene（场次） | 特定人物在某个时间、地点和局面下的一段互动情境 | 默认属于剧情作品，拥有稳定局部 ID |
| Lore Entry（设定条目，原草案称 Knowledge Entry） | 一条可单独引用、由作者整理的创作信息 | 默认属于 Character、World、Lorebook 或剧情作品，随所属作品发布 |
| Lorebook（设定集） | 作者整理的一组设定条目 | 可独立发布，条目仍可分别引用 |
| Knowledge Source（参考资料） | 可被引用的原始或长篇材料，如设定文档、年表、书籍章节 | 先作为作品关联的资料资源；独立资料包的发布粒度待定 |
| Scenario（剧情作品，暂沿用现有名字） | 将人物、场次、剧情线、时间安排与资料组织在一起的作品 | 可独立发布 |

“场景”在讨论中容易同时指地点、一次情境和整部剧目。本文用 Scene 指场次：旅馆大厅是地点，“停电后众人在大厅对质”是场次，“雨夜旅馆”是剧情作品。是否继续使用 Scenario 作为产品名称另行评审。

对象具有稳定 ID，不等于每个对象都要拥有独立发布、作者主页或版本生命周期。作者可以直接在作品里写一段场次或一条设定，无需先创建额外作品。

资料与条目的区分依据是作者如何提供和使用内容，不是文件扩展名或长度阈值。Lore Entry 可以引用其资料来源，也可以直接原创；Knowledge Source 也可以直接供 Runtime 查询，无需强制先生成 Lorebook。

## 4. Character：可引用的人物资料

建议最小创作入口为名字与一段介绍。推荐但可选的内容栏目包括外貌、性格与行为倾向、动机、背景经历、表达方式、示例对白。栏目内主要是自然语言，作者也可以增加有标题的自定义章节。

建议的结构成分：

- 身份：稳定 ID、名称、别名、简介和形象资源。
- 人物正文：介绍及可选主题栏目。
- 关联：世界、其他人物、关系及相关设定条目。
- 默认创作搭配：作者可选的开场情境或相关作品引用；不要求一个人物只能属于一个剧情。

与特定剧目绑定的处境、临时目的和局部改编放在该剧目中；人物本身长期成立的背景可以保留在 Character。分界依据是适用范围，而非“目标必须放在哪个固定字段”。不要在人物背景与多个 Lore 条目中各维护一份相同的权威正文；需要复用时建立引用。

报告建议的 identity / profile / dialogue 分区可作为编辑器引导，但年龄、职业、价值观等不必全部成为强制核心字段。示例对白应支持具名参与者，不能只固定为 user/assistant。人物行为描述仍属于创作内容；报告示例中的 system role、消息位置和优先级应留在独立策略中，避免与现有 Preset 职责重叠。

示例：“Alice 做事谨慎，说话常留余地”可以属于人物；“在今晚的盘问中，Alice 想保护昨夜离开的旅客”属于这部剧情对 Alice 的安排。

## 5. Scene：一段有条件与矛盾的互动情境

Scene 的最小内容是标题与局面描述。时间、地点、参与人物、关联资料和剧情作用在相关时补充，不应强制所有场次都有所有字段。

| 建议字段 | 用途 | 示例 |
|---|---|---|
| id / title | 可引用身份与名称 | lobby / 停电后的大厅 |
| place | 地点引用，或尚未独立整理的地点说明 | 旅馆大厅 |
| time | 时间说明、事件引用或相对顺序 | 第一夜，停电之后 |
| participants | 本作品中参与者的引用 | Alice、Bob、玩家 |
| setup | 这一场开始时的局面 | 道路封闭，众人发现一名住客失踪 |
| intentions / tensions | 人物的本场目的与矛盾 | Alice 想隐瞒；Bob 想追问 |
| lore / sources | 与本场有关的条目、资料引用和初始知情安排 | Alice 知道旅客去了哪里 |
| dramatic_intent | 作者希望探索的变化，可选 | 让对话逐渐显露证词矛盾 |
| beats | 本场或剧情线希望涉及的关键变化，可选 | 玩家开始怀疑证词；Alice 面临是否坦白的抉择 |
| possibilities | 可能发展、转折或后续场次，可选 | 坦白、搜查、继续隐瞒 |

dramatic_intent 和 possibilities 属于作者的创作安排，其默认语义应为指导与可能性，不能被编译器自动升级成必定发生的结果。确有明确分支或固定事件时应另行清楚标注，其求值与约束语义需要单独设计。

一个 Scene 可以没有预写对白、没有选项按钮、没有明确出口。结构应允许这种开放情境，也允许作者写精确的对白和分支。所有人的实际回应及这次游玩发生的结果归 Runtime。

## 6. Knowledge：资料来源、设定条目与知情关系

原草案将 knowledge 直接称为“设定条目”，范围过窄。结合研究报告和 Data Bank 文档后，建议在新模型中使用更明确的名称：Knowledge Source 表示参考资料，Lore Entry 表示作者整理的设定条目，“人物知情”表示人物与信息的关系。这是 char.pub 的候选语义，不是跨软件已统一的标准。

例如，《旅馆建筑与历史》是参考资料，“后门通向河边”是作者从中整理出的条目，“Alice 知道后门”是本作品中的知情安排。

Knowledge Source 的候选信息是：稳定 ID、标题、资料内容或资产引用、出处、可选的引用段落定位及用途说明。来源链接若指向可变内容，应在发布时明确所用资料版本或快照。来源包含某项陈述，不自动代表本作品将其采纳为事实；正文相互矛盾时也不能靠检索排序替作者选择。

Lore Entry 最小包含稳定局部 ID、标题和正文。可选信息包括：关于哪些人物或地点、标签与别名、适用世界或时期、信息性质及叙述来源。信息性质可以区分作者确定的设定、传闻或人物的说法；这不意味着要为每句话建立事实数据库。

适合成为条目的例子：旅馆有一条后门通道；城中居民信奉某种禁忌；某人物经历过一次事故。每条内容应有足够独立的含义，避免拆成大量脱离上下文的句子。

必须分别回答三个问题：

1. 条目描述了什么？例如“昨夜旅客从后门离开”。
2. 在这部作品的起点，谁知道或相信它？例如 Alice 知道，Bob 不知道。这项安排放在人物或剧情使用该条目的位置。
3. 本轮模型是否需要获得它？这是消费端根据当前情境、叙事视角和预算决定的事情。

未声明某人是否知情，不自动等于此人不知道。关键词命中也不意味着人物因此学会了信息。作者设定的秘密不等同于平台访问权限：Runtime 仍须区分叙述者获得信息与角色在故事中知情。

对于传闻，“城民相信后门闹鬼”可以是真实存在的说法，“后门真的有鬼”则是另一项作者需要决定的内容。结构允许保留这种区别，不自动把所有正文当作事实。

## 7. Lorebook：整理与复用条目的集合

Lorebook 建议包含名称、介绍、条目列表及可选分组。条目可在集合中直接创建，也可引用其他已发布作品中的条目；跨作品引用沿用明确版本与来源。重复引用同一条内容不会创造第二份正文。

典型例子包括“港城风俗”“旅馆建筑与历史”“某人物的往事”。同一世界可以有多个 Lorebook，一部剧情也可以组合多个 Lorebook。World 表达世界自身的设定与关联，Lorebook 表达作者如何整理一组信息，不应要求二者一一对应。

Lorebook 不是默认公开给所有角色的知识，也不是必须每轮整体注入的文本。选择一个 Lorebook 代表引入一组可用资料；本作品如何使用、哪些人知情、何时提供给模型需要各自的语义。

原草案只强调集合，低估了作者安排资料使用方式的需求。结合报告，建议同时表达条目内容及其使用声明：关于哪些人物和场次、在什么范围内持续重要、是否为可选背景、哪些人最初知情。别名、关键词等相关性线索也可以保留。严格的信息边界与普通相关性提示需要区别，不能全部降为可忽略的建议。

插入深度、预算、embedding 模型、rerank、概率采样等具体策略由消费配置和 Runtime 表达。SillyTavern 的原有触发与注入配置可以在兼容数据中保留，不静默删除；不支持的语义需报告。这里不要求普通创作者理解每个 Runtime 的参数。

导入时不能自动把指令、情绪控制文本等包装成世界事实；保留原文与来源，必要的分类由作者确认。

## 8. 一份串起四者的示意

以下 YAML 只展示结构关系。短引用为说明用别名，未指定新协议语法；真实发布需要补齐身份、来源及外部 Release 锁。

```yaml
characters:
  alice:
    name: Alice
    overview: 一位谨慎而有同情心的旅馆老板。
    voice: 说话温和，遇到敏感问题常留余地。

lorebooks:
  inn-notes:
    title: 旅馆资料
    entries:
      back-door:
        title: 旅馆后门
        body: 后门通向河边的小路，外来客通常不知道这条路。

scenario:
  title: 雨夜旅馆
  cast:
    host:
      character: character:alice
      situation: 今晚想保护昨夜离开的旅客。
    visitor:
      supplied_by: player

  lore:
    guest-departure:
      title: 昨夜的离开
      body: Alice 昨夜帮助那名旅客从后门离开。

  scenes:
    lobby:
      title: 停电后的大厅
      place: 旅馆大厅
      time: 第一夜，停电之后
      participants: [cast:host, cast:visitor]
      setup: 暴风雪封路，玩家向 Alice 询问失踪的住客。
      lore:
        - ref: lorebook:inn-notes#back-door
        - ref: lore:guest-departure
          initially_known_to: [cast:host]
          initially_unknown_to: [cast:visitor]
      dramatic_intent: 探索 Alice 的自保与同情心之间的矛盾。
      possibilities:
        - Alice 因为信任玩家而透露部分真相。
        - 玩家提出搜查，迫使 Alice 面对更直接的压力。
```

这里人物定义、资料集合、剧情自己的秘密和具体场次各有位置。Alice 的原作不必包含本剧目的秘密；可能的发展也没有被写成唯一允许的玩家行动。

## 9. Beat、剧情线与时间线如何接上

Scene 回答人物在什么局面下互动；Beat 回答作者希望出现什么关键变化。例如“雨夜大厅的盘问”是一场戏，“玩家开始怀疑 Alice 的证词”是一个剧情节拍。节拍的表达不必指定哪句台词造成怀疑，也不要求每条模型回复都完成一个节拍。

Beat 可以是一个场次内的安排，也可以在剧情线上引用并关联相关场次。相同节拍不在多个视图里复制定义。某些节拍是作者期待探索的方向，某些是明确可选的转折；需要硬性保证的事件另行声明，不能仅凭排序就把所有节拍解释为必须发生。

人物弧线也可先用“戒备 → 犹豫 → 愿意承担风险”等定性描述，并关联这些节拍。报告里的 trust=0.28、anger=0.67 是一种可选的数值机制。首版允许作者自行声明变量及其效果（见总稿第 14.2 节），但变量不是普通人物或场次的必填项，平台也不预设统一的情感量纲。

剧情线可以引用 Scene，组织主线、支线和人物变化。同一个场次可以关联多个剧情线，不必复制正文。

时间线组织事件发生的顺序，可先允许“昨夜”“第一夜”这类相对时间，不强制填写日期。叙事顺序描述作者如何安排揭示过程。某事件的正文只保留一个权威定义，时间线与场次通过引用关联它。

已经发生的背景事件，与作者预期或可能发生的后续事件应可辨识；一次游玩的实际事件历史由 Runtime 维护。这些关联不要求每条玩家回复对应一个剧情节点。

## 10. 与现有仓库的关系及设计检验

现有 Creation/Release 身份、精确引用、来源和许可机制可以继续使用。当前 Character、World、Lorebook 以 Fragment 为主要正文单元，Scenario 已有 cast 和引用。Fragment 可继续承担有身份的正文，但单靠 knowledge/scenario 的 kind 标签及 activation 不能表达本文的全部关联。

本文区分 Knowledge Source 与 Lore Entry 是候选模型的命名澄清，不改变现有 `fragment.kind = knowledge` 的解释。旧 knowledge 片段仍可对应设定条目；参考资料的资产、来源与引用契约需单独补充，不能直接把旧条目重新解释成长篇资料。

后续需要决定候选字段如何映射到现有 Fragment、类型专属结构与公开产物。不能同时把 profile、Fragment 和导出文本都当作分别可编辑的权威副本。先选定创作数据的权威表示，再生成模型消费的视图。

迁移应先保留现有自由文本、ID、来源和兼容配置；让作者逐步增加关联。不能凭模型推断自动把旧角色描述拆成未经作者认可的事实，也不能宣称导出到 CCv3 后还保有完整场次和剧情线语义。

设计可以用这些例子核对，而不必先开发 Runtime：

- 一个角色只写简介，也能成为完整作品。
- 同一个地点有两个不同场次，参与者与矛盾可以不同。
- 同一条信息可以被不同人物知晓、误解或尚不知晓。
- 两个 Lorebook 引用同一条目，正文、版本和来源仍明确。
- 一个场次既推动主线，也影响人物关系，不复制成两份。
- 没有预写选项和结局的开放场景可以发布。
- 原角色被用于新剧情时，新剧情的秘密与临时目标不污染原角色。

首轮需要评审的重点是上述语义与默认粒度。字段命名、Scene 是否需要独立发布、信息性质的枚举以及严格分支契约可以在这些例子达成共识后收敛。

## 11. 对 deep-research-report 的取舍

报告覆盖生态、发布基础设施、创作模型和 Runtime。它提供了研究线索及候选方案，不构成一份全部已被成熟工具验证的数据标准。其中 Scene/Plot 必须状态机化、数值情感曲线、SemVer、插件市场及技术栈是建议；官方工具的能力存在，也不能证明这些建议都应进入 char.pub。

本次复核集中于 Data Bank、World Info 以及 AI Dungeon Scenario、Story Cards、Plot Essentials 的相关内容语义；未全面重验报告中的软件版本、服务状态、商业规划、法律或技术选型结论。报告中的旧引用标记不是本项目可直接解析的来源索引，正式设计依据应使用可访问的原始文档链接。

| 报告建议 | 本草案的处理 |
|---|---|
| 超越单张角色卡，支持独立内容与组合发布 | 吸收。沿用已有 Creation/Release 与来源、引用、锁定机制，不因 package 比喻另起一套发布身份 |
| Knowledge package 与 Lorebook 有区别 | 吸收概念区别；先明确资料、条目和集合，不预先把每一种都升级成顶层作品类型 |
| Lore 条目包含激活与注入信息 | 补充作者的使用声明并保留兼容配置；内容含义、使用边界和具体 Runtime 参数各有明确位置 |
| Scene/Plot 必须引入状态机 | 调整为开放场次与可选节拍/分支；首版提供可选的声明式条件与效果，需要严格条件的作品可以声明，不能作为所有 RP 创作的前提 |
| emotionalArc 用数值表达 | 保留人物变化的创作需求；默认允许定性描述，数值规则按具体作品需要另行设计 |
| character、scene、plot、bundle 等全部独立包化 | 不整体采纳。发布粒度依据独立复用、归属及版本需求决定，内部对象首先拥有稳定引用 |
| Character 内声明 system promptBlocks | 调整为人物正文与独立 Preset/Prompt Module 的关联，保留现有内容/策略边界 |
| Scenario 是启动多个 Adventure 的模板 | 吸收定义与实例的边界。发布起始安排与可用内容，实际游玩经历归独立 Runtime |
| 双版本、SemVer 及行为影响等级 | 保留“格式兼容不等于创作含义不变”的提醒；不据此推翻当前版本 label 与精确 pin。行为变化说明可辅助作者判断，不能保证生成行为兼容 |
| Runtime 插件、记忆策略和真实行为测试 | 本轮不纳入创作核心模型；实际会话、记忆及执行归 Runtime，可发布内容与可执行代码的边界保持明确 |

修订后的组织关系可以概括为：

```text
可复用的创作内容：人物、世界、关系、设定集、参考资料
                     ↓ 引用与本作品内的安排
剧情作品：参与人物、场次、剧情线、关键节拍、时间安排
                     ↓ 附带作者的使用意图与必要边界
发布产物：静态创作定义、资源、来源与版本锁
                     ↓ 消费
独立 Runtime：上下文编排与一次实际游玩
```

这些是逻辑职责而非新增微服务、包类型或必须分离的文件。编辑器可以提供人物页、资料页、场景卡与时间线等视图，视图共同操作同一组内容和引用。
