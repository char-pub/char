# Roleplay 深度优化决策

## 目标与范围

用户在 2026-10-05 指出：作品内容太少，Harness 对人物、场景和故事的展现不足，渐进暴露与 Roleplay 优化不够，要求继续深度优化。本轮覆盖 char.pub 内容/上下文引擎与独立 Harness 的消费体验。

用户随后明确答复“好，开始吧”，确认第一轮先做深 2002 年一章，并同步实现可复用的 Harness 能力。基础上下文修复已完成；继续实施剧情回合、玩家视角、渐进内容和界面，并验证连续游玩与恢复。现有生产版及旧存档保持不变。

## 已确定的背景

- 既有体验选择保留：玩家扮演山上徹也；保留真实背景，允许改写开局后的走向；模拟对白和分支不能冒充公开事实。
- 发布版是六个独立历史开局：一个 beat、四个 choices、一个变量，没有阶段结局或贯穿场次的后果。
- 公开产物六个开局的可选目录均为空；现有素材基本为 pinned 正文。可选目录、模型检索和逐步发现尚无真实内容输入。
- Core 已支持条件、typed effects、一次性确认、场次进入、知情和结局；自由文本不会自动产生确认。
- Harness 已支持成功结算后的持久状态、幂等和中断恢复；App 目前只提交文本 input。Jev/Laya 没有承担自由文本到 Story operation 的完整转换。
- Harness 只在开局加载 Source 正文；动态选取新的 Source 需要每回合的正文获取与持久输入记录。
- Source 的现有可见性不足以按年代或人物知情严格隐藏目录。第一章若使用语义 fragments，可以复用已有场次和知情过滤。
- 官方 DeepSeek adapter 把 system 消息视为完整快照；Roleplay 的多段 system 是共同组成提示的片段。当前 profile 的能力声明不匹配。

## 决策

- 保留现有职责：char.pub 管理静态作品与纯语义，Harness 管理游玩回合、模型调用、存档和展示。没有证据支持合并两者或重写通用 AgentLoop。
- 不把场次关联当执行条件。每个可确认的剧情目标都应声明年代/场次、先决事实和分支条件；模型判断只能补充明确的待判断叶子。
- 叙事文本、正式状态和玩家界面必须可核对。模型写出一个变化不代表该变化已提交；失败和不确定结果不能部分推进。
- 不把叙事者完整上下文直接当玩家侧栏。玩家已知信息、其他角色秘密、未来情节分别投影。
- 当前生产版保留原样。后续内容以新版本或新作品交付，不覆盖既有 Release 或玩家存档。
- 第一轮采用 2002 年一章做纵向体验。20–30 回合是容量与检验样本，不是强迫剧情拖延的规则；实现必须可用于其他作者作品。

## 工作假设

- 第一章优先用内嵌语义 fragments 实现按需发现，避免立即扩大 Source 可见性和持久化协议；后续根据真实资料需求决定。
- 先测量长回合上下文和恢复成本；只有实际达到预算限制时才设计带来源的记忆 checkpoint，不静默裁剪历史。

## 阶段结局的确认方式

2026-10-05 的真实模型对照中，flash 和更强的 pro 都曾把准备或修改草案误判为确认采用。用户据此明确选择：仅阶段结局增加明确确认按钮，普通对话和场景继续自动推进。

因此，模型可以提出待确认的阶段结果，但不能仅凭自然语言判断就提交结局。待确认内容应随成功回合持久保存；刷新后可继续确认，后续修改应使旧提案失效。确认必须绑定当前版本、支持幂等查询和撤回。它不变成每回合的强制确认弹窗。
